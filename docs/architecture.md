# Architecture

This document describes the structure of the `cli-multiregnskab` repository.
It uses Simplified Technical English (ASD-STE100) style. Sentences are short.
Each sentence gives one fact or one instruction.

## Glossary

Use these terms with the meanings below. Do not use other words for the same idea.

| Term | Meaning |
|---|---|
| the spec | The file `public-client-api-v1.yaml`. It describes the Multiregnskab API in the OpenAPI format. |
| the API package | The package `packages/api` (`@holmconsulting-dk/multiregnskab-api`). |
| the CLI package | The package `packages/cli` (`mr`, `@holmconsulting/cli-multiregnskab`). |
| a consumer | Any program that uses the API package. Examples: the CLI package, an MCP server. |
| an operation | A hand-written function in the API package. An operation calls one or more spec endpoints and adds validation and error handling. |
| MCP | Model Context Protocol. A protocol that lets AI agents call tools over a defined interface. |

## Overview

The repository is a Bun workspace. It has two packages.

- The API package holds all code that talks to the Multiregnskab backend.
- The CLI package holds the `mr` command-line tool. It uses the API package to do its work.

Other consumers, for example an MCP server, can also use the API package.
The API package does not depend on the CLI package or on any one consumer.

## Two layers inside the API package

The API package has two layers. Each layer has a different purpose and a different update process.

### Layer 1: Generated types

File: `packages/api/src/types.ts`.

This layer gives TypeScript types for every endpoint and every data shape in the spec.
A tool builds this file. Do not edit this file by hand.

The build step works like this:

1. The tool `openapi-typescript` reads `public-client-api-v1.yaml`.
2. The tool writes matching TypeScript types to `types.ts`.
3. Run this step with the command `bun run generate-api`.

This layer does not contain business logic. It does not choose default values.
It does not validate input. It only describes shapes.

Because this step is mechanical, it is safe to automate. A scheduled job can fetch a new
spec, run `generate-api`, and open a pull request with the result. A person must still
review the change before merge, because a new or changed endpoint may need a new or
changed operation. See Layer 2.

### Layer 2: Operations

Folder: `packages/api/src/operations/`.

This layer wraps the generated types into functions that a consumer can call directly.
A person writes this layer by hand. A person must update it when the spec adds a new
capability or changes an existing one in a way that affects behavior.

Each operation provides:

- **A name and a description.** These identify the operation to a consumer, for example
  an MCP tool list.
- **An input schema**, written with `zod`. This validates caller input at runtime.
  The spec's `required` field is not always correct. The input schema can enforce
  stricter rules than the spec states.
- **Consistent error handling.** On failure, an operation throws `ApiOperationError`.
  This error carries the HTTP response and the response body. Every consumer can handle
  errors the same way.
- **Business rules that the spec does not state.** Example: an invoice line must always
  include `productTypeXid`, even when `productXid` is also present. This rule comes from
  real API behavior, not from the spec text. See "Known API quirks" in the project's
  `CLAUDE.md` file for the current list of such rules.

`packages/api/src/operations/index.ts` collects all operations into one list. A consumer,
for example the CLI package, imports this list and calls `.execute()` on the operations
it needs.

### Why the split matters

The two layers change at different speeds and for different reasons.

- Layer 1 changes whenever the spec changes. The change is mechanical and low-risk.
- Layer 2 changes only when new behavior is needed, or when a spec change affects an
  existing operation. The change needs human judgment.

Keeping the layers separate lets the project automate Layer 1 safely, without also
automating Layer 2. Automating Layer 2 is not safe, because a type-level change in the
spec does not always show the full effect of a real API change.

## How the CLI package uses this

Commands in `packages/cli/src/commands/<area>/<command>.ts` call operations from the API
package. A command's action function calls `.execute()` on an operation and reports the
result or the error to the user.

Each area also has an `info` subcommand. This is the primary place for usage guidance,
required fields, examples, and known issues. Put this material in the `info` subcommand
text, not in a separate document.

## Release process

The repository has two independent release pipelines. Both pipelines trigger on a
git tag push.

| Tag pattern | Pipeline | Output |
|---|---|---|
| `v*` | `release.yml` | CLI binaries for macOS, Linux, and Windows, attached to a GitHub release |
| `api-v*` | `publish-api.yml` | The API package, published to GitHub Packages |

A change to Layer 1 or Layer 2 in the API package needs an `api-v*` tag to reach
consumers. A change to the CLI package needs a `v*` tag to reach users.
